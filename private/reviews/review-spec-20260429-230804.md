## Findings

### 🔴 Critical
1. [docs/specs/spec-multi-repo-workspace-model.md:1421-1432, 1471] — **`OrphanPending` lifecycle contradicts daemon-restart recovery text**.
   - Startup recovery says “for each registry row in `Active` or `OrphanPending` … If the leaf heartbeat file is fresh … the row remains `Active`” (lines 1421–1432).
   - The lifecycle table claims `OrphanPending` exits only to `CleaningUp` (line 1471).
   This is a spec-level correctness bug: it’s unclear whether a row that becomes `OrphanPending` can ever return to `Active` when liveness is positively *alive*.

   **Fix (exact replacement text):**

   Replace lines **1430–1432** with:
   ```text
   2. If the leaf heartbeat file is fresh (mtime within
      `2 × heartbeat_interval` of `now`), the row MUST be `Active`.
      If the row is currently `OrphanPending`, the daemon MUST transition it
      back to `Active`; the runner is presumed to have outlived the daemon.
   ```

   Replace line **1471** (the `OrphanPending` row in the lifecycle table) with:
   ```text
   | `OrphanPending` | enters from: `Creating` (reconcile/startup), `Active` (reconcile), `CleaningUp` (cleanup-time inconclusive) | `Active` (if a subsequent §3.6 step 4 probe observes liveness as Alive / heartbeat fresh), or `CleaningUp` (when liveness is positively disproved and reconcile drains the `OrphanReclaim` queue and re-enters §3.6 from step 3); from `CleaningUp` then to row removed (terminal) or `CleanupFailed` | Reconcile re-probes; `OrphanPending` is not sticky if liveness becomes provably alive. |
   ```

3. [docs/specs/spec-multi-repo-workspace-model.md:1914-1917, 2011-2017] — **Reconcile loop wording contradicts itself**.
   - Step 7 says reconcile “does NOT scan the registry by Status column for reclamation work” (lines 1915–1917).
   - A few lines later it states reconcile re-evaluates `OrphanPending`/`CleanupFailed` rows (lines 2011–2017), which implies a status-driven scan.

   **Fix (exact replacement text):** Replace lines **1914–1917** with:
   ```text
   A background reconcile task (cadence: `2 × heartbeat_interval`, default 10s)
   operates by **draining the `OrphanReclaim` in-memory queue end-to-end for
   cleanup execution** — the queue is the ONLY mechanism that invokes
   `cleanup_workspace(_, OrphanReclaim, …)`. Separately, on the same cadence,
   reconcile MAY scan the registry for rows in `Status::OrphanPending` and
   `Status::CleanupFailed` per §5B.1 to re-run probes and enqueue new
   `OrphanReclaim` work; it MUST NOT perform destructive cleanup directly from
   that scan.
   ```

### 🟢 Suggestions
1. [docs/specs/spec-multi-repo-workspace-model.md:517-522] — **Inline re-probe error taxonomy is incomplete**.
   The §3.5 step 5b inline re-probe only specifies `ENOENT`/`ELOOP` handling for `openat`; other failures are not specified.

   **Fix (exact replacement text):** Replace lines **517–522** with:
   ```text
   below). On `ENOENT` / `ELOOP` from the `openat` (the leaf
   vanished or was replaced by a symlink between `mkdirat`'s
   `EEXIST` and this re-probe), the row is treated as
   `OrphanedNoLeaf` and the enqueue proceeds without re-probe (the
   no-leaf condition makes liveness moot). On any other error from
   `openat` or from the fd-anchored probes of §3.6 step 4, the probe
   result is treated as `Inconclusive` (fail-closed): the orchestrator
   MUST NOT enqueue and MUST return `Error::WorkspaceBusy`.
   The `leaf_fd` MUST be closed before this step continues.
   ```
