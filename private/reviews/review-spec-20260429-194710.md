## Findings

### 🔴 Critical
None.

### 🟡 Important
1. [1349] `supports_acp` contradicts §3.4 explicit negotiation by allowing a follow-up-frame switch.
   **Fix:** Replace the row with: `| \`supports_acp\` | Informational capability bit only. It indicates the agent implementation can speak the Agent Coding Protocol, but ACP MUST be selected only by explicit spawn-time negotiation per §3.4. The runner MUST NOT switch transports based on this bit alone, on any follow-up frame, or by silent fallback from ACP to JSONL. |`
2. [736-738] `ε₁` is defined as Stage-1 enqueue budget, but the parenthetical measures until first SIGTERM dispatch, which spans later stages and contradicts lines 753-766 and T-1.
   **Fix:** Replace the bullet with: `- \`ε₁\` — Stage-1 enqueue budget: the maximum time allowed for \`enqueue_outbound_control\` to deliver the cooperative \`cancel\` frame before StopCascade escalates to Stage 2. Default **≥ 100 ms**, configurable via \`shutdown_enqueue_budget_ms\`.`
3. [2300-2314] §8.2 still frames ACP version handling as unresolved even though §3.4 already normatively selects hard-refuse and rejects JSONL fallback.
   **Fix:** Replace §8.2 with: `### 8.2 ACP version pinning policy\n\nResolved for v1: if an agent advertises an ACP version \`caduceusd\` does not implement, the daemon MUST reject with \`unsupported_acp_version\` and proceed with \`stop_cascade(reason = "acp_version_mismatch")\` per §3.4. Silent fallback to JSONL is forbidden. Future versions MAY specify negotiated downgrade only if ACP itself standardises a backward-compatible version-selection rule; v1 does not permit it.`

### 🟢 Suggestions
1. [326-352, 439-492, 576-601] Make validation precedence explicit as a single normative rule.
   **Fix:** Add after line 325: `Validation order is normative and first-match-wins: for each inbound frame the runner MUST evaluate, in order, parse/outer-envelope validity, \`run_id\` identity, agent \`seq\` contiguity, handshake/T-4 handling, capability/env consistency, tool-use capability guard (N-3), and finally closed-set \`event.kind\` enforcement. On the first failing check, the runner MUST emit the associated diagnostic, stop or drop as specified, and MUST NOT continue evaluating later checks for that frame.`
2. [439-457, 576-601] Pre-handshake unknown kinds are handled correctly, but only implicitly through T-4 then the closed-set guard.
   **Fix:** Append to the T-4 comment: `A first frame with an unknown non-\`handshake\` kind is therefore re-processed under \`most_restrictive()\` and then rejected by the closed-set \`unknown_message_kind\` guard below; there is no separate permissive pre-handshake path.`
3. [493-509, 1988-2015] Env↔handshake tool-use disagreement is defined, but precedence could be spelled out.
   **Fix:** Add after line 493: `This consistency check runs only after \`run_id\`, outer-seq, and handshake-payload parsing succeed; if multiple defects coexist on one frame, the earlier validation order above determines the emitted reason.`
