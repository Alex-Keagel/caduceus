## Findings

### 🔴 Critical
1. [docs/specs/spec-caduceus-agent-runner-contract.md:867-874] — §3.4 still specifies unsupported ACP version as an in-session handshake error + StopCascade path, but §8.2 now normatively says unsupported ACP is a hard spawn refusal with no JSONL fallback. This is an interoperability/implementability conflict in transport selection.
   **Fix:**
   ```text
   **Version negotiation.** If the agent advertises an ACP version the
   daemon does not implement, the daemon MUST emit an
   `unsupported_acp_version` diagnostic/event, MUST return a spawn-time
   error to the upstream caller, and MUST NOT silently fall back to JSONL
   once ACP has been requested. If a runner process was already started
   for ACP negotiation, the daemon MUST reap it before returning.
   Unsupported ACP version is a hard refusal-to-run condition, not a
   recoverable in-session transport error.
   ```

### 🟡 Important
1. [docs/specs/spec-caduceus-agent-runner-contract.md:758-775] — The shutdown-budget prose still misbinds stages/tunables: it says “Stage-2 SIGTERM dispatch is bounded by ε₂” and explains the `2·grace_period_ms` term using a nonexistent “Stage-1 grace”. The per-stage decomposition below is correct, so this section is self-contradictory.
   **Fix:**
   ```text
   - `ε₁` — Stage-1 enqueue latency budget. ε₁ is the budget for
     enqueuing-or-skipping the Stage-1 `cancel` control message
     (whichever applies under §3.5 cancellation policy) once the daemon
     has decided to cancel the run; it does NOT measure time to first
     SIGTERM. Time from cancel-decision to SIGTERM dispatch is bounded
     by ε₁ + grace_period_ms (Stage 1 enqueue/skip + Stage 2
     stdin-close grace); see the per-stage decomposition below.
     Default **≥ 100 ms**, configurable via `shutdown_enqueue_budget_ms`.
   ```
   and
   ```text
   The factor of 2 covers the two grace windows that can stack in the worst
   case: Stage 2 (stdin-close→voluntary-exit, `grace_period_ms`) and Stage 3a
   (SIGTERM→reap, `grace_period_ms`). Every cite of this bound in
   §5 / §6 / I-3 / T-1 / T-9 MUST use this exact expression and refer back to §3.3.
   ```

2. [docs/specs/spec-caduceus-agent-runner-contract.md:469-474, 1382-1384] — The handshake parser comment still says an “unknown bit” makes the handshake malformed, but §4.2 says undocumented capability bits are informational-only and MUST NOT change behavior. That is a forward-compat contradiction.
   **Fix:**
   ```text
   // Malformed handshake payload: line was
   // valid JSONL (otherwise try_parse_jsonl
   // above would have fired `malformed_jsonl`),
   // but the capabilities sub-schema is
   // invalid (wrong type for a known bit,
   // missing required field, …). Unknown
   // capability bits are NOT an error here;
   // per §4.2 they MUST be ignored as
   // informational-only forward-compat fields.
   // Fail-closed:
   ```

That misdocuments the load-bearing invariant.

4. [docs/specs/spec-caduceus-agent-runner-contract.md:2124-2137] — The test matrix still lacks a case for the now-normative “unsupported ACP version hard-refuses spawn” rule, so the §8.2 fix can regress silently.
