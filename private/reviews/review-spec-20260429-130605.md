## Findings

### 🔴 Critical
1. [§5 I-7, line ~1369] — Invariant still says hook failure MUST remove leaf before return. This now conflicts with §3.5 step 1b/10 where `CleanupOwnershipFailed` or `ParentRevalidationFailed` retain row as `CleanupFailed` for reconcile.
   **Fix (exact replacement):**
   `- **I-7 (Rollback safety on hook failure).** If \`before_create\` or \`after_create\` fails, \`create_workspace\` MUST execute §3.5 step 10 inline rollback and MUST return the original hook error (\`Error::HookFailed\` or \`Error::HookTimeout\`), not a rollback error. If rollback reaches step 10c, the leaf is removed and the placeholder row is deleted before return. If rollback aborts earlier with \`Error::CleanupOwnershipFailed\` or \`Error::ParentRevalidationFailed\`, the row MUST transition to \`Status::CleanupFailed\` and be retained for reconcile (§4.3).`

2. [Appendix C failure variant, line 1918] — Says “registry row removed” unconditionally immediately after sentence that allows CleanupFailed deferral.
   **Fix (exact replacement):**
   `- Locks released. If rollback reached §3.5 step 10c, the placeholder row is removed; if rollback stopped early with \`Error::CleanupOwnershipFailed\` or \`Error::ParentRevalidationFailed\`, the row remains as \`Status::CleanupFailed\` for reconcile.`
