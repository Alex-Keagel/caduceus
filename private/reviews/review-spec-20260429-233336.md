## Findings

### 🔴 Critical
1. [docs/specs/spec-orchestrator-status-snapshot.md:121,408-411,2293-2352] `RingEviction` and `LockStepTrimRace` are not disjoint. Both describe a lock-step trim evicting an under-replay window, so a conforming implementation cannot deterministically choose one. **Fix:** Replace the terms-table entry and enum with a two-reason model:

   `| **ReplayCancelReason** | Discriminator on \`PostAckFrame::ReplayCancelled\` indicating why a clause-(d) replay was aborted: \`RingTrimEviction\` (lock-step ring trim — index AND payload buffer — evicted at least one \`stream_seq\` in the under-replay window \`(s_c, current_stream_seq_at_cancel]\`; this is the only reason raised when Z-29 lock-step trim runs while a replay is in flight; tested by T-31 and T-31b), \`BufferEviction\` (the replay index still covers the requested window but the payload could not be materialized — checksum failure, in-flight rebuild, or read fault; no trim involved; tested by T-31a). Both reasons terminate the post-ack stream and require subscriber re-subscribe via clause (c). |`

   ```rust
   enum ReplayCancelReason {
       RingTrimEviction,
       BufferEviction,
   }
   ```

   Update T-31/T-31b to use `RingTrimEviction`.

2. [docs/specs/spec-orchestrator-status-snapshot.md:941-951] Z-29 boot-edge routing is not total. The tuple `current_stream_seq == 0`, `since_stream_seq == Some(0)`, same boot, and mismatched non-`None` fingerprint matches none of (a)/(P)/(b)/(c)/(d)/(d′). **Fix:** Replace lines 941-951 with:

   `- **Z-29 boot edge case.** When \`current_stream_seq == 0\`, the replay index and delta payload buffer are empty and \`ring_oldest_seq\` is undefined. In this regime, the reachable routing outcomes are:`
   `  - (b) — explicit boot mismatch (\`since_boot_id = Some(other)\` and \`other != daemon.boot_id\`).`
   `  - (a) — future cursor (\`since_stream_seq = Some(s_c)\` with \`s_c > 0\`).`
   `  - (c) — \`since_fingerprint == None\`.`
   `  - vacuous-\`UpToDate\` — \`s_c == 0 && since_fingerprint == Some(current_fingerprint) && since_boot_id ∈ {Some(daemon.boot_id), None}\`.`
   `  - malformed-same-boot mismatch — \`s_c == 0 && since_fingerprint == Some(fp_x) && fp_x != current_fingerprint && since_boot_id ∈ {Some(daemon.boot_id), None}\`. The daemon MUST route this tuple through clause (c)'s recovery path (full \`Resync\`); it MUST NOT route to (d′), which requires a non-empty replay index.`
   ``
   Clauses (P), (d), and (d′) cannot fire at boot because the replay index is empty; treat `ring_oldest_seq := current_stream_seq + 1` when the index is empty, so clause (P)'s predicate is unsatisfied.
   ``

### 🟡 Important
1. [docs/specs/spec-orchestrator-status-snapshot.md:2341-2357] T-31b still leaves `affected` undefined, does not define the trim visibility point, and does not say how already-buffered delta frames ahead of the cancel frame are handled. **Fix:** Replace lines 2341-2357 with:

   `*Atomicity contract (write-before-trim, owning-task-local).* Trim runs on the orchestrator's owning task. Define the affected replay-subscriber set \`A\` at trim entry as every subscriber whose per-subscriber send queue is in replay mode, whose pending replay window \`(s_c, current_stream_seq_at_cancel]\` intersects the set of \`stream_seq\` values to be evicted by this trim, and whose stream is not already closed at trim entry. For every subscriber in \`A\`, the trim operation MUST: (1) drain any unsent \`PostAckFrame::Delta\` frames already enqueued for that subscriber; (2) enqueue exactly one \`PostAckFrame::ReplayCancelled { stream_seq: current_stream_seq_at_cancel, reason: ReplayCancelReason::RingTrimEviction }\` on a reserved terminal-control slot; and (3) mark the per-subscriber send queue closed for further enqueues. Only after steps 1-3 complete for every subscriber in \`A\` MAY the trim become observable to other readers (advance \`ring_oldest_seq\` and release the evicted index/payload entries). The daemon MUST NOT wait for subscriber-side receipt or ACKs.`

2. [docs/specs/spec-orchestrator-status-snapshot.md:883-904,2293-2352] The replay-cancel contract is duplicated across §3.4, T-31, T-31a, and T-31b, and the copies are already drifting. **Fix:** Replace the normative test prose in T-31/T-31a/T-31b with a single sentence in each section: `Verifies the §3.4 replay-cancellation-frame contract under <trigger>.` Keep the MUST-level wording only in §3.4.

3. [docs/specs/spec-orchestrator-status-snapshot.md:857-878,1251-1304] Replay-mode buffering reserves per-subscriber control capacity but never caps aggregate replay-buffer memory. **Fix:** Add this invariant under §5 and reference it from §3.4: `The daemon MUST cap aggregate replay-mode per-subscriber buffering at \`replay_buffer_total_bytes\` (default 64 MiB, configurable). When admitting a new replay-mode subscriber or buffering a new live delta would exceed the cap, the daemon MUST emit \`ReplayCancelled { reason: BufferEviction }\` to the oldest replay-mode subscriber and close that stream. The daemon MUST NOT block the publish path on replay-mode buffer pressure.`
