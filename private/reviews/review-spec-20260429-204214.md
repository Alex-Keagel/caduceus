## Findings

### 🔴 Critical
1. [docs/specs/spec-caduceus-orchestrator-algorithm.md:1136-1142] — `next_attempt_number` is still wrong for retry-bound exits. The helper says "last `FinishedRunSummary`.attempt + 1, or 1 if none exists," but retry-bound exits do **not** write a ring entry (`1365-1366`). After a `Normal` or `Abnormal` exit, the next dispatch would therefore re-use attempt `1`, violating the monotonic-per-run attempt contract (`106-109`, `1138-1139`) and breaking attempt-based freshness fencing in §3.5/§8.7.
   **Fix:**
   ```rust
   /// `next_attempt_number(state, run_id) -> u32`:
   ///   Returns the dispatch-attempt number to assign to the next
   ///   `RunningEntry` for `run_id`. It MUST increase monotonically for
   ///   a given `run_id` within one daemon process.
   ///
   ///   Compute it as follows, in order:
   ///   1. If `state.retry_attempts[run_id]` exists, return
   ///      `state.retry_attempts[run_id].attempt + 1`.
   ///   2. Else if `recent_history_ring` contains a prior
   ///      `FinishedRunSummary` for `run_id`, return
   ///      `summary.attempt + 1` from the most recent such summary.
   ///   3. Else return `1`.
   ```

2. [docs/specs/spec-caduceus-orchestrator-algorithm.md:697-713,1149-1154] — `next_retry_attempt` is defined against `state.running[run_id]`, but `on_worker_exit` removes that entry before calling the helper. As written, the normative helper is unimplementable at its only call site.
   **Fix:**
   ```rust
   /// `next_retry_attempt(entry: &RunningEntry) -> u32`:
   ///   Returns the next retry ordinal for the attempt that just exited,
   ///   equal to `entry.current_retry_attempt + 1`.
   ///   The caller MUST pass the `RunningEntry` removed from
   ///   `state.running` at the start of `on_worker_exit`; implementations
   ///   MUST NOT re-read `state.running[run_id]` or
   ///   `state.retry_attempts[run_id]` to compute this value.
   ```
   and
   ```rust
   let n = next_retry_attempt(&entry);
   ```

3. [docs/specs/spec-caduceus-orchestrator-algorithm.md:818-877] — `on_retry_timer` fetches the run and immediately calls `dispatch_run` without classifying `Terminal` vs `Neither` vs `Active`. That leaves a real hole: a run that becomes `Terminal` or `Neither` while waiting in `retry_attempts` is invisible to reconcile (`§3.2` only scans `state.running`) and can loop through `Deferred`/Z-9 abandon instead of taking the mandatory cascade path. For `Terminal`, this violates I-5 (`1725-1735`) because workspace cleanup never runs.
   **Fix:** insert this block after `let run = runs.into_iter().next().unwrap();` and before the concurrency check:
   ```rust
   match state.work_source.classify(&run) {
       TrackerClass::Terminal => {
           state.claimed.remove(&run_id);
           state.retry_attempts.remove(&run_id);
           state.dispatch_defer_attempts.remove(&run_id);
           state.token_totals.remove(&run_id);
           state.last_reported_tokens.remove(&run_id);
           cleanup_workspace(&run_id, state).await;
           log_diagnostic(
               "on_retry_timer observed Terminal run before redispatch",
               run_id = &run_id,
           );
           return;
       }
       TrackerClass::Neither => {
           state.claimed.remove(&run_id);
           state.retry_attempts.remove(&run_id);
           state.dispatch_defer_attempts.remove(&run_id);
           state.token_totals.remove(&run_id);
           state.last_reported_tokens.remove(&run_id);
           log_diagnostic(
               "on_retry_timer observed run leave query before redispatch",
               run_id = &run_id,
           );
           return;
       }
       TrackerClass::Active => {}
   }
   ```
