## Findings

### 🔴 Critical

1. **[Lines 1136-1142, 708-719, 757-764, 1365-1366] `next_attempt_number` is still underspecified and its recommended computation is wrong for retry-bound exits.**
   The helper says implementations SHOULD compute the next dispatch attempt from the latest `FinishedRunSummary.attempt` in `recent_history_ring`. But the spec also says non-terminal exits that schedule a retry do **not** push to the ring (**1365-1366**). After a normal or abnormal exit, the retry entry is created at **757-764** and the next dispatch will occur without any new ring summary, so the recommended ring-based computation can repeat attempt numbers and violate the helper's own monotonicity requirement.

   **Fix:** replace the helper text with:

   ```rust
   /// `next_attempt_number(state, run_id) -> u32`:
   ///   Returns the dispatch-attempt number to assign to a newly-spawned
   ///   `RunningEntry` for `run_id`. It MUST increase monotonically for
   ///   a given `run_id` within a daemon process.
   ///
   ///   Compute it as follows:
   ///   1. If `state.retry_attempts[run_id]` exists, return
   ///      `state.retry_attempts[run_id].attempt + 1`.
   ///      (`RetryEntry.attempt` is the retry ordinal that produced the
   ///      pending re-dispatch, so the new worker attempt is exactly one
   ///      higher.)
   ///   2. Otherwise, if `recent_history_ring` contains a prior
   ///      `FinishedRunSummary` for `run_id`, return
   ///      `last_summary.attempt + 1`.
   ///   3. Otherwise return `1`.
   ///
   ///   Implementations MUST NOT maintain a parallel per-run attempt map;
   ///   the sources of truth are the pending `RetryEntry` (between
   ///   attempts) and `recent_history_ring` (after a terminal finalize).
   ```

2. **[Lines 697-713, 1149-1154] `next_retry_attempt` is defined in terms of state that no longer exists at its only call site.**
   `on_worker_exit` removes the live entry at **697-700**, then in the abnormal arm calls `next_retry_attempt(state, &run_id)` at **713**. But the helper says it returns `state.running[run_id].current_retry_attempt + 1` (**1149-1154**). At that point `state.running[run_id]` has already been removed, so the normative helper cannot be implemented as written.

   **Fix:** replace the helper text and call site with:

   ```rust
   let n = next_retry_attempt(&entry);    // 1, 2, 3, …
   ```

   ```rust
   /// `next_retry_attempt(entry: &RunningEntry) -> u32`:
   ///   Returns the next retry ordinal for the attempt that just exited,
   ///   equal to `entry.current_retry_attempt + 1`.
   ///   `on_worker_exit` MUST compute this from the removed `RunningEntry`;
   ///   implementations MUST NOT re-read `state.running[run_id]` or
   ///   `state.retry_attempts[run_id]` here.
   ```

3. **[Lines 818-877, 1725-1736] `on_retry_timer` can silently bypass terminal/neither handling between attempts.**
   The retry timer fetches the run by id and dispatches it directly (**825-877**) without classifying it. If the WorkSource has moved the run to `Terminal` or `Neither` after the previous attempt exited but before the retry fires, `on_retry_timer` never invokes the terminal/left-query cleanup rules from invariant **I-5** (**1725-1736**). Instead it falls into `dispatch_run` / `Deferred`, keeping the run claimed until repeated defers or abandoning it without the required cleanup semantics.

   **Fix:** insert a classification gate after `let run = runs.into_iter().next().unwrap();`:

   ```rust
   match state.work_source.classify(&run) {
       TrackerClass::Terminal => {
           cleanup_workspace(&run_id, state).await;
           state.claimed.remove(&run_id);
           state.retry_attempts.remove(&run_id);
           state.dispatch_defer_attempts.remove(&run_id);
           state.token_totals.remove(&run_id);
           state.last_reported_tokens.remove(&run_id);
           return;
       }
       TrackerClass::Neither => {
           state.claimed.remove(&run_id);
           state.retry_attempts.remove(&run_id);
           state.dispatch_defer_attempts.remove(&run_id);
           state.token_totals.remove(&run_id);
           state.last_reported_tokens.remove(&run_id);
           return;
       }
       TrackerClass::Active => {}
   }
   ```

### 🟡 Important

1. **[Lines 775, 781-782, 924, 1635] Several section references are stale.**
   `terminate_and_finish` lives in §3.1, not §3.5; ring invariant #5 lives in §4, not §3.5 or §6; `SubscribeAck` is not defined in this spec's §3.4. These are navigation defects, not semantic blockers.

## Recommended Actions

1. Fix `next_attempt_number` so it derives from `retry_attempts` between attempts and the ring after terminal finalize.
2. Change `next_retry_attempt` to consume `RunningEntry` rather than re-reading state after removal.
3. Add a retry-path classification gate for `Terminal` / `Neither` before redispatch.
4. Clean up stale section references after the blocking fixes land.
