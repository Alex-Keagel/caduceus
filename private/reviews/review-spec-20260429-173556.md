## Findings

### �� Critical
1. [L1579-L1584 vs L193-L213] — `boot_id` lifecycle still contradicts startup pseudocode. Startup validates first, then allocates `OrchestratorState`; lifecycle text still says `boot_id` is generated before validation. **Fix:** Replace item 1 with:

   > 1. *Generation point.* `boot_id` is generated exactly once in `start_service` (§3.1) via `Uuid::new_v4()`, as part of the single `OrchestratorState` allocation that occurs only after `validate_dispatch_config(&config)` succeeds. A config-validation failure aborts startup before any state, including `boot_id`, is allocated. No subscriber can observe an uninitialised `boot_id` because mailbox binding happens only after the constructed `state` exists.

2. [L323-L349] — `terminate_and_finish` still self-contradicts: postcondition 4 says the ring always gets exactly one new entry, but the same section says the absent-run early return writes no ring entry. **Fix:** Replace postcondition 4 and the carve-out paragraph with:

   > 4. If `run_id ∈ state.running` at entry, `state.recent_history_ring` has had **exactly one** new `FinishedRunSummary` appended whose `run_id` equals the argument and whose `exit_reason == ExitReason::DaemonTerminated { cause }` for the supplied `cause` (eviction MAY have occurred per §4 ring invariants, but the new entry is at the tail). If `run_id ∉ state.running` at entry, the helper short-circuits at the early return and **no** ring entry is written.
   >
   > If the helper is invoked on a `run_id` that is not in `state.running` (early-return at L298), postconditions 1–3 and 5–8 are trivially satisfied and postcondition 4's no-write clause applies. This is what preserves exactly one terminal ring entry across racing cascade arms.

### 🟡 Important
1. [L570, L602, L707] — `next_attempt_number`, `prior_retry_attempt`, and `next_retry_attempt` are still normatively referenced but never defined. An implementer must invent their semantics. **Fix:** Insert immediately after the `prior_restart_count` docstring:

   ```rust
   /// `next_attempt_number(state, run_id)` scans `recent_history_ring` for the
   /// most recent `FinishedRunSummary` whose `run_id` matches and returns
   /// `summary.attempt + 1`; if no entry exists, it returns `1`.
   ///
   /// `prior_retry_attempt(state, run_id)` returns
   /// `state.retry_attempts.get(run_id).map(|r| r.attempt).unwrap_or(0)`.
   ///
   /// `next_retry_attempt(state, run_id)` returns
   /// `state.retry_attempts.get(run_id).map(|r| r.attempt + 1).unwrap_or(1)`.
   ```

2. [L859-L867 vs L947-L950] — retry requeue on saturated concurrency updates `reason` but not `scheduled_at`, so RetryRow can expose stale schedule metadata while the timer is re-armed. **Fix:** Replace the `and_modify` block with:

   ```rust
   state.retry_attempts.entry(run_id.clone()).and_modify(|r| {
       r.reason       = "no available orchestrator slots".into();
       r.scheduled_at = Instant::now()
           + Duration::from_millis(state.config.poll_interval_ms);
   });
   ```
