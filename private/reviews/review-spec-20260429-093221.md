## Findings

### 🔴 Critical

1. **§3.6 step 3 uses `leaf_fd` before it is opened.** Step 3 (liveness check) reads the heartbeat via `fstatat(leaf_fd, ".caduceus-heartbeat", AT_SYMLINK_NOFOLLOW)` (lines 716, 1105). But `leaf_fd` is opened in **step 4** (lines 767–768). Step 3 runs first. As written, every conformant implementation must either (a) open a private leaf_fd for liveness and re-open in step 4, or (b) reorder steps 3↔4. Neither is currently mandated. Worse: an implementation that reads the impl-prose literally will pass an uninitialized fd to `fstatat` and either crash or sample an unrelated kernel fd, returning false-fresh for arbitrary workspaces.
   **Fix:** Replace the §3.6 algorithm preamble with this ordering:
   > 1. Acquire per-workspace lock.
   > 2. Re-validate path.
   > 3. **Open `parent_fd` and `leaf_fd`** (§3.6 step 4 fd-acquisition prelude — moved up, runs before liveness probe).
   > 4. Liveness check (now operates on `leaf_fd` from step 3).
   > 5. Run `before_cleanup` hook with the same fds.
   > 6. Re-validate path …
   >
   > i.e. promote what is currently §3.6 step 4's fd-open prelude *above* the liveness check, leave hook execution where it is. Update line 716 to read `fstatat(leaf_fd /* opened in step 3 */, …)`. Update §5B.1 row "CleaningUp" to reflect the new step numbers.

2. **F5 vs §5A.2 / §3.8: heartbeat write is impossible in default deployment.** §5A.4 (F5) says hooks default to daemon uid. §3.5 step 5a (line 415) creates the leaf via `mkdirat(slug_fd, run_id, 0o755)` — owned by daemon uid because the daemon ran the syscall. §5A.2 row 4 (line 1316) says the leaf is "Owner: runner uid (after `after_create`)" but "v1 does not enforce this". §3.8 (line 955) says the heartbeat is "Owned by the spawned runner uid" via `fchown` or "by virtue of the runner's effective uid at create time". With hooks running as daemon uid (F5 default) and no enforced chown, the runner uid (distinct per §5A.4 SHOULD) lands in a 0755 daemon-uid-owned leaf. **A non-owner cannot create files in a 0755 directory.** `openat(leaf_fd, ".caduceus-heartbeat", O_CREAT, 0o600)` returns `EACCES`. The heartbeat — the *primary* liveness signal per §3.6 step 3 N-4 — is never written. Every workspace immediately becomes "heartbeat unreadable" → fail-closed → `OrphanPending` → never reclaimable.
   **Fix:** §5A.4 must add a normative step between hook execution and runner spawn:
   > **Leaf-ownership handoff (normative).** Before `spawn_worker` (spec #1 §3.3) is invoked, the daemon MUST `fchownat(slug_fd, sanitize_run_id(run_id), runner_uid, runner_gid, AT_SYMLINK_NOFOLLOW)` against the leaf, then `fchmodat` it to `0700`. This handoff runs as daemon uid (which owns the leaf at this point) and is the only way the runner uid can subsequently create the heartbeat file at `0600`. If `hooks.run_as = runner_uid`, the chown is still required because the leaf was `mkdirat`'d as the daemon uid (step 5a runs before any uid drop). Spec #6 SHOULD recommend, and a future revision MUST require, that workflows omit any chown logic from `after_create` since the daemon now owns the handoff.
   >
   > Cross-link from §5A.2 row 4 ("Owner: runner uid (after `after_create`)") to §5A.4 leaf-ownership handoff and remove "v1 does not enforce this" — v1 MUST enforce, otherwise heartbeat liveness is non-functional.

3. **F4 inode reassertion ignores `st_dev` — bind-mount swap defeats it.** §3.5 step 5b (lines 435–441) and §3.6 step 4 (line 757) compare `st_ino` only. An attacker (or operator with bind-mount privilege) who replaces `<workspace_root>/<slug>` with a bind mount of a directory whose root inode happens to equal the captured `parent_st_ino` (trivial under attacker control of the new fs) passes the check. `st_ino` collisions across `st_dev` are routine — every newly-formatted filesystem has an inode 2 root.
   **Fix:** In §3.5 step 5a, additionally capture `parent_st_dev = fstatat_result.st_dev` and persist alongside `parent_inode` in the registry (rename the registry field to `parent_dev_inode: Option<(u64, u64)>`, or add `parent_dev: Option<u64>`). Update §3.5 step 5b's reassertion to `(st_dev, st_ino) == (parent_st_dev, parent_st_ino)`. Update §3.6 step 4 likewise. Update §5A.1 threat T-C wording to mention bind-mount swap explicitly. Note the OQ-1 tension: this is *not* the same as cross-fs path validation; it is dev+inode equality on the slug parent and is normative regardless of OQ-1's outcome.

### 🟡 Important

4. **F1 leaf scan has no exclusion for `<slug>/.bare/` or reserved `<slug>/.cache/`.** §5B.2 step 5 (lines 1423–1438) walks "all first-level slug directories" and treats every child as a `<run_id>` candidate. Under §3.7 strategy (c), `<workspace_root>/<slug>/.bare/` is a real bare git checkout that is not a Run leaf. The scan would enqueue `OrphanReclaim { slug, run_id: ".bare" }` and the reconciler would attempt `cleanup_workspace` against the bare repo, deleting it. §4.1 also reserves `<slug>/.cache/`.
   **Fix:** §5B.2 step 5 sub-bullet: "Reserved-prefix or non-directory entries are logged and skipped" — strengthen to:
   > **Reserved-prefix exemption (normative).** Within each `<workspace_root>/<slug>/`, entries whose name starts with `.` (e.g. `.bare`, `.cache`, future `.caduceus-*`) MUST be skipped by the leaf scan AND MUST NOT be enqueued for `OrphanReclaim`. Run leaves are guaranteed by §3.2 not to start with `.` (sanitize_run_id rejects leading dots); any dotfile under `<slug>/` is either a strategy-(c) artifact, a reserved daemon cache, or operator state, none of which the reconcile queue may target. A `<slug>` directory whose only contents are dotfiles is treated as "no run leaves present" and skipped.
   >
   > Cross-link to §3.2 (run_id sanitization) to make the leading-dot-rejection load-bearing.

5. **F3 reserved-key collision is enforced only in §3.6 step 7 — not in §3.5 step 6.** F3 normative text at lines 815–824 says "This applies to all four hooks (`before_create`, `after_create`, `before_cleanup`, `after_cleanup`)" but the asymmetry is real: §3.5 step 6 (the create-side hook env) lacks any reserved-key collision policy. An implementation that reads §3.5 step 6 in isolation has no obligation to fail-closed on a workflow forwarding `CADUCEUS_REPO_REMOTE_URL=evil`.
   **Fix:** Insert at the end of §3.5 step 6, immediately before the `PATH` bullet:
   > **Reserved-key collision (normative).** Identical semantics to §3.6 step 7: any workflow-declared env-forwarding entry whose key matches `CADUCEUS_*` or any of the reserved keys listed above MUST cause the hook spawn to fail with `Error::HookEnvConflict { key }` and emit a `CRITICAL` log. The check applies symmetrically to `before_create` and `after_create`.
   >
   > Update §4.4 error taxonomy `HookEnvConflict` "Source §" cell from "§3.6 step 7" to "§3.5 step 6 / §3.6 step 7".

6. **Duplicate `OrphanReclaim` enqueue race after F2.** §3.5 step 5b returns `Error::WorkspaceBusyOrReclaiming` after enqueueing OrphanReclaim. Step 10d releases the per-slug guard. A retry of `create_workspace(slug, run_id, …)` arriving before the reconciler drains the queue acquires the per-slug guard, hits EEXIST again at step 5b, and enqueues a *second* OrphanReclaim for the same `(slug, run_id)`. Reconcile queue semantics are unspecified (§4.5 mentions the queue but defines no dedup). Two cleanup_workspace invocations on the same row racing is currently safe (cleanup is idempotent under per-workspace lock) but the wording does not promise this.
   **Fix:** Add to §4.5 (or §5B.2 step 7 reconcile loop):
   > **OrphanReclaim queue dedup (normative).** The reconcile queue MUST be keyed on `(slug, sanitized_run_id)` with set semantics — duplicate enqueues for an already-queued or in-flight tuple MUST be coalesced. The reconciler holds the per-workspace lock for the duration of a single reclaim, so a duplicate enqueue arriving mid-reclaim either (a) sees the in-flight reclaim's per-workspace lock held and waits, or (b) is dropped because the row no longer exists post-reclaim. Implementations MUST NOT enqueue blindly without dedup; an unbounded retry storm is a conformance failure.

7. **Step 10's parent-inode revalidation in §3.5 step 10a uses `parent_st_ino` captured in step 5a — but step 5a may not have run if the failure was upstream.** §3.5 step 10a says "If `leaf_fd` was successfully opened in step 5c, walk it … skip this sub-step otherwise". OK for leaf cases. But the step 10a revalidation block (lines 590–605) reads as if `parent_st_ino` is always available. If step 5a returned `Error::SymlinkEscape` mid-call (e.g. `fstatat` reported `S_ISLNK`), step 5a never persisted `parent_st_ino` into local scope and step 10a can't `fstatat`-revalidate against an unset value. The text doesn't gate this.
   **Fix:** Prepend to §3.5 step 10a:
   > Sub-step 10a applies only when step 5a successfully captured `parent_st_ino` (i.e. step 5a's `fstatat` reported `S_ISDIR`). If step 5a aborted with `SymlinkEscape` before capture, the rollback skips both the leaf walk and the parent revalidation; only the placeholder removal in 10c runs. Locks are released per 10d as usual.

8. **F6 legacy `parent_inode==None` TOFU has a TOCTOU window of its own.** §3.6 step 4 (lines 759–766) says on `parent_inode == None`, persist current fstatat result and proceed. Between the persist (under per-workspace lock) and any subsequent destructive op, the persisted value is now treated as authoritative — but it was obtained at a moment when an attacker could have already swapped the slug parent. TOFU is the right call for legacy migration, but the wording doesn't acknowledge that the first cleanup of a legacy row offers no parent-swap protection.
   **Fix:** Append to the F6 paragraph (lines 759–766):
   > **Legacy-row caveat (informative).** TOFU on a legacy `parent_inode == None` row provides no defence against parent-swap that occurred prior to the first post-migration cleanup; it merely bootstraps the field for *subsequent* cleanups. Operators concerned about this gap MAY force-migrate by triggering a no-op `cleanup_workspace(_, OperatorRequested)` against every legacy row at upgrade time, which captures parent_inode under the operator's known-clean conditions. This is non-normative; reconcile MUST NOT auto-trigger such a migration.

### 🟢 Suggestions

9. **TOCTOU defense restated three times.** §3.5 step 5 prose, §3.5 "TOCTOU defense (normative summary)", and §5A.3 table all enumerate the same fd-anchored disciplines. Pick one canonical home (§5A.3 is the right one) and reduce the others to cross-references. Saves ~40 lines and removes drift risk on future edits.

10. **Z-N / gpt-N-N / N-N / ITER3-FOLLOWUP / ITER4-FOLLOWUP anchors leak iteration history into normative text.** A reader who didn't sit through iterations 1–4 has no way to interpret "Z-15 implication" (line 505) or "gpt-N-3 fix" (line 565). These anchors are review artefacts, not specification content.
    **Fix:** Move all anchors to a single Appendix E ("Iteration provenance") that maps anchor → iteration → fix description, and replace every in-text anchor with a stable section-cross-reference (e.g. "see §4.2 `last_heartbeat_at` persistence requirement" instead of "Z-15"). This is mechanical, but should not happen in this review pass — it is a polish iteration after Correctness/Security findings 1–3 land.

11. **§5A.4 says daemon "MUST NOT run as root in production" — but no startup check enforces it.** §5B.2 step 2 audits workspace_root mode but not daemon uid. A `setcap`'d non-root daemon is arguably equivalent for `CAP_DAC_READ_SEARCH`, but a literal `root`-running daemon is a deployment footgun the spec forbids without enforcing.
    **Fix:** Add to §5B.2 step 2:
    > Verify the daemon's effective uid is non-zero. Effective uid 0 ⇒ refuse to start with `Error::DaemonUidPrivileged` (new) unless an explicit `allow_root_daemon: true` config flag is set (operators on platforms without uid separation, e.g. embedded hosts). Add `DaemonUidPrivileged` to §4.4 error taxonomy.

12. **Heartbeat-file `fchown` flow is hand-wavy.** §3.8 (lines 955–957) says heartbeat is "Owned by the spawned runner uid (set via `fchown` on the fd before the first write, or by virtue of the runner's effective uid at create time)". The "or" is doing too much work — these are different threat profiles. If `fchown` is performed by the daemon (daemon uid creates the fd, then fchown's to runner uid before handoff), only daemon uid can write between create and handoff (small window, fine). If the runner creates it as its own uid, the leaf must already be runner-owned (finding 2). The spec should pick one and require it.
    **Fix:** Land finding 2's leaf-ownership handoff first, then state §3.8 unambiguously: "The heartbeat file is created by the runner via `openat(leaf_fd, …, O_CREAT, 0o600)` after the daemon's leaf-ownership handoff (§5A.4) has chowned the leaf to runner uid. The file is owned by runner uid by virtue of the creating process's effective uid; no `fchown` is required."
